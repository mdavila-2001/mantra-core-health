## 0. Resumen ejecutivo (lo que cambia respecto de «hay que construirlo»)

1. **Casi todo lo que pide este frente ya existe en alguna rama; mucho ya está en `dev` y en `test`.** El perfil admin de `claude/stoic-johnson-4vl5bf` (motor `bulk_import`, ciclo de vida de usuarios, «quién puede qué», simulador) **está mergeado** en `dev` y `test` de los dos repos (front #1761/#1770; API #1176). El `TRASPASO.md` que decía «sin mergear, conflictos add/add» quedó desactualizado el mismo 31/10 (`merge: traer dev a la rama…`, `c34dc6d55`).
2. **El hueco grande es un desbalance front/API.** El gobierno de accesos IGA (cuatro ojos, campañas de certificación, SoD, reglas, ciclo de vida del equipo, explicar/simular, matriz, anomalías) está **en el front de `dev` y `test`** (PR #1754 y #1765, 154 archivos en `features/access-governance/`) y **en el modelo de `dev`** (parches v4275/v4278/v4279, commit `dae1a9a`), pero **la API no**: el PR de la API #1175 salió contra `master`, quedó `dirty` y está **cerrado sin mergear**. Hoy el front de `dev` llama 60+ rutas (`/org/team/*`, `/org/access-reviews/campaigns`, `/approvals/pending`, `/org/governance/*`, `/org/access/explain|simulate`, `/org/lifecycle/cases`) que **no existen en la API de `dev`**: contra la API real esas pantallas caen en S5/S9. Esto es lo primero a cerrar.
3. **Cargas masivas:** el motor está completo y probado contra dobles (117 `it()`), pero **no persiste** (`InMemoryBatchRepository`) ni **da de alta a nadie** (`NotConnected*`), y lo bloquea la **tabla del lote** que no existe en el modelo. La pantalla del front existe, sin spec y sin captura. La carga masiva de **farmacia** (FAR-05) sí está terminada, mergeada y con Playwright de idempotencia; la de **terminología** también. No hay cuatro ojos sobre lotes.
4. **Aprobación/revisión:** no hay un motor único. Hay **al menos 9 implementaciones ad hoc** en la API de `dev` (catálogo, moderación, identidad, accesos clínicos, delegaciones, break-glass, cambios de plataforma sin controlador, QA, ERP) y una décima —la más completa, `four_eyes_requests` con `payload_hash`, vencimiento y consumo atómico— sólo en la rama de API sin mergear. **El plan la toma como base del motor único** en lugar de inventar otro.
5. **Gobierno de usuarios:** la API de `dev` ya tiene ciclo de vida con motivo obligatorio, revocación de sesiones y auditoría (`iam-users.controller.ts:483-583`), y la sesión de un suspendido **cae de verdad** en el siguiente request (`session-validator.ts:50-66`). El front **no lo consume**: ninguna pantalla llama a `suspend/reactivate/deactivate`, `access-map`, `access-reviews` ni `simulations`. Falta la pestaña, no la API.

## 5. Cómo se prueba que funciona de verdad

Todo contra Postgres + Redis + API real (`docker-compose.yml` perfil `local-db`), nunca contra el simulador. Evidencia: request y response del navegador (`trazos`), consulta SQL por `E2E_REAL_DB`, captura antes/después de recargar.

1. **Lote real de usuarios.** `PLATFORM_ADMIN` sube `ok-50.csv` de `usuario-paciente` → `POST /admin/bulk-imports` 201 `VALIDADO` (50 válidas) → confirma con `Idempotency-Key: K1` → 202 + `approvalId` (si aplica H3) → **otro** `SECURITY_ADMIN` aprueba en `/administration/access-governance/approvals` → lote `COMPLETADO` → `SELECT count(*) FROM iam.users WHERE created_at > :t0` = 50 y `SELECT count(*) FROM audit.audit_log WHERE action = 'BULK_IMPORT_ROW_CREATED' AND detail_json->>'batchId' = :id` = 50 → `GET :id/report` sin tokens ni documentos → recarga de la pantalla: mismo lote, mismos contadores. **Segundo envío idéntico** con `K1` → 200 el mismo lote; con `K2` → 50 `OMITIDA` (duplicado), `count(*)` sigue en 50. Reinicio de la API durante `PROCESANDO` → el lote termina igual.
2. **Autoaprobación.** El mismo admin intenta aprobar su lote → 403 `FOUR_EYES_SELF_APPROVAL`; decidir dos veces → 409; dejar vencer → `EXPIRED` tras el barrido.
3. **Suspender usuario.** Con una sesión abierta del usuario U (token T): `POST /iam/users/U/suspend {reason}` 200 `revokedSessions ≥ 1` → `GET /authz/me/access` con T → **401 `SESSION_INACTIVE`** (`session-validator.ts:50-66`) → `GET /iam/users/U/lifecycle` muestra `SUSPENDED` con motivo y actor → `POST reactivate` (vía cuatro ojos si H3) → login nuevo de U → 200. Sin motivo → 400; `SECURITY_ADMIN` acotado a una organización → 403 (`PlatformAdminScopeGuard`); `DEACTIVATE` → `reactivate` → 412.
4. **Simulador = decisión real.** Mismo cuerpo a `POST /authz/simulations` y `POST /authz/decisions/evaluate` → `decision` idéntica para: permitido, denegado por falta de permiso, denegado por campo restringido, denegado por IP (si H1 trae `ip-access-rules`). La pantalla muestra las dos y una prueba las compara.
5. **Quién puede qué.** Conceder `bulk_import.users` a un rol → `GET /authz/permissions/:id/holders` lo lista con `source: ROLE` → revocar → desaparece → `GET /audit/log` tiene ambas acciones.
6. **Gobierno de organización (H1).** `gobierno-api-real.spec.ts` 13/13 y `hospital-piloto-api-real.spec.ts` 17/17 sobre la base recargada 04→07→09.
7. **Gates por franja.** `yarn lint` · `yarn typecheck` · `yarn build` · specs dirigidos · `check-*.mjs` a mano · Playwright sin `networkidle` · capturas 3 viewports × 2 temas con doble revisión por otro agente · consola y red sin errores nuevos · dos PRs.
