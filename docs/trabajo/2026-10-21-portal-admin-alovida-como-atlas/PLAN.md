# Plan — Inventario y portal interno de AloVida con la anatomía de AtlasAdminPortal

- Fecha: 2026-10-21 · Repos afectados: `mantra-core-health-api` (generadores + API real del portal), `mantra-core-health-model` (catálogo de datos y deriva), `mantra-core-health` (portal en Angular) · Rama en los tres: `claude-marcelo/vigilant-bardeen-gcoocw` · Predecesor: ninguno en AloVida. **Referencia de anatomía**: `PasanakuFrontend/docs/trabajo/2026-10-18-backoffice-como-atlas/` (`evidencia/atlas-inventario.md` = las 129 rutas de Atlas; `evidencia/sistema-visual.md` = anatomías de listado, ficha y shell).
- Resultado observable: un operador con rol de plataforma abre el **portal interno de AloVida** y encuentra, con la misma organización de menú y la misma anatomía de pantalla que `AtlasAdminPortal`, (1) el **catálogo de operaciones**: las 1 190 operaciones HTTP reales con ficha de 6 pestañas — qué tablas toca, qué DTO restringe cada dato, qué exige, payload mínimo, para qué sirve en negocio y en sistema, y a qué flujo pertenece; (2) el **mapa de flujos**: cada flujo con su diagrama, y dentro de cada operación su árbol de decisión; (3) el **catálogo de datos**: tablas, columnas, relaciones e índices con su función, y el linaje operación → tabla. Todo servido por el API real, no por el mock.
- Kill-test: abrir `administration/portal/sistemas/operaciones/<id de POST /scheduling/slots/{id}/holds>`; si la pestaña «Tablas impactadas» no lista `scheduling.slot_holds` y `scheduling.slots` con operación y si la pestaña «Resumen» no dice a qué flujo pertenece («Ciclo de vida de una cita») con enlace al diagrama, **no está hecho**. Segundo kill-test: apagar el mock (`start:real-api`) y que la pantalla siga mostrando datos.

### 3. Hipótesis (se confirman en la microtarea indicada; ninguna se presenta como hecho)
- **H-1** `system_ops.entity_registry` / `field_registry` alcanzan para persistir estado, revisión, responsable y retención de la ficha de catálogo sin crear tablas nuevas → se confirma en H4.S1.M1 leyendo las entidades.
- **H-2** La cadena controlador → servicio → repositorio → entidad se puede resolver estáticamente para la gran mayoría de las 1 190 operaciones (el repo es NestJS con capas finas: «Capa fina: valida parámetros y delega», `audit.controller.ts:37`) → se mide en H1.S2.M3; lo que no se resuelva queda marcado `NO_RESUELTO`, nunca inventado.
- **H-3** Un «flujo» se puede reconstruir de forma útil con tres fuentes: la tabla UC del README del módulo (agrupa endpoints), las excepciones y condiciones del servicio (árbol de decisión) y los eventos/outbox (efectos) → se valida con el módulo piloto en H2.S1.
- **H-4** Un renderer de grafos propio en SVG con layout por capas alcanza para los diagramas de flujo y de linaje a la escala de un módulo (≤ 80 nodos) → se decide con el piloto de H5.S3.M1; si no alcanza, se registra un ADR para incorporar `elkjs` (regla 95.1.4).

## Decisiones
- **D-01 Inventario como artefacto generado, no escrito a mano.** Tres generadores en `api/tools/inventario/` (`endpoints.mjs`, `flujos.mjs`, `catalogo.mjs`) emiten JSON versionado en `api/inventario/` y markdown en `api/docs/inventario/`. Lo curado (texto revisado, decisiones) vive aparte en la base (`system_ops`) y se superpone en lectura; nunca se edita el JSON generado (misma separación «inventario técnico / narrativa curada» que ya usa `model/docs/data-catalog/README.md`).
- **D-02 Las fuentes se citan en cada fila.** Cada endpoint, flujo, tabla y columna lleva `fuente` (archivo:línea o `.puml`) y `confianza` (`DECLARADO` si sale de un decorador/DDL, `DERIVADO` si sale del análisis estático, `NO_RESUELTO` si no se pudo). Prohibido rellenar con heurísticas de nombre sin marcarlas (regla 00 §2).
- **D-03 El modelo consume el repo hermano**, como ya hace `tools/catalog` con `SALUD_VAULT`: `MODEL_ROOT` apunta a `../mantra-core-health-model`; sin él, el generador de catálogo falla con mensaje, no inventa.
- **D-04 El API real reemplaza al mock ruta por ruta.** Módulo nuevo `admin_portal` (schema de lectura, sin tablas propias) que sirve los JSON cargados al arranque y superpone lo persistido en `system_ops`. El mock de `/admin/catalog/*` se retira cuando la ruta real pasa su prueba de integración; mientras tanto convive (ADR-0014 del frontend: portadas que se gradúan).
- **D-05 Grafos sin librería nueva** (hipótesis H-4): componente `graph-canvas` propio (SVG + layout por capas tipo Sugiyama simplificado, pan/zoom, buscador que centra un nodo, cajón de detalle). Si el piloto no rinde, ADR para `elkjs`. En docs, Mermaid (ya instalado en `mkdocs`).
- **D-06 Reusar primitivas antes de crear** (CLAUDE.md del frontend): `page-header`, `filter-bar`, `data-table`, `pagination`, `tabs`, `fact-section`, `view-state-host`, `breadcrumb`. Se crean sólo: `drawer-panel`, `confirm-dialog` (frase opcional), `metric-card` (ícono+tono+pista), insignias semánticas (`method-badge`, `risk-badge`, `pii-badge`, `review-badge`, `block-badge`), `key-value-section` (si `fact-section` no cubre cebra + mono copiable; se verifica en H5.S1.M1), `graph-canvas`.
- **D-07 Riesgo y PII se derivan con regla declarada, no a ojo**: riesgo `ALTO` si escribe en tabla con PII o financiera o es pública con escritura; `MEDIO` si escribe; `BAJO` si sólo lee. PII por columna: `field_registry` / `data_classifications` si existen; si no, **sin dato** (no heurística por nombre). La regla queda escrita en `api/docs/inventario/README.md`.
